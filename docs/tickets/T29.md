# T29: Every CI job has a time limit

[#78](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/issues/78) · PR [#79](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/pull/79) · draft PR, in review

Every job in every workflow now sets `timeout-minutes`, and a test fails if one doesn't, so a hung test costs at most 20 minutes of CI rather than GitHub's default of 6 hours.

## Spec

Found in the review of PR #76: no workflow set a limit, and pytest has no timeout of its own.

- **Done when:**
  - Every job in every file under `.github/workflows/` sets `timeout-minutes`: 20 for `test`, 5 for `answer-key`, and 30 for the Claude jobs.
  - A test fails if a job in any workflow has no `timeout-minutes`, and it adds no dependency.
  - A job that goes past its limit fails rather than passes. This rests on GitHub's documented behaviour; the record says it wasn't shown live.
- **Decisions:**
  - **The numbers:** the human approved 20, 5 and 30, sized from the issue's figure that the slowest of the last 31 PR runs of CI took 235 seconds. **Correction:** that figure is out of date, and the issue's text stays as it is. Run [41875685515](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/actions/runs/41875685515) later took 243 seconds, of which its `test` job took 240. Measured per job with `gh api` on 2026-11-05 at 02:40Z, every attempt of every `pull_request` run still listed, back to 2026-10-29:

    | Job | Runs | Slowest passing | Note |
    |---|---|---|---|
    | `test` | 120 | 240 s | One attempt reached the limit at 1218 s and ended `cancelled` (see Evidence) |
    | `answer-key` | 120 | 10 s | |
    | `claude-review` | 87 | 183 s | Some of these skipped the review, as on this PR, so this isn't a reliable worst case |
    | `claude` | none | not measured | It doesn't run on `pull_request` |

    A job's time here runs from `started_at` to `completed_at`, so its wait in the queue isn't part of it. The longest wait was 15 s. 20 minutes is five times 240 seconds, so the agreed limits still fit.
  - **Which jobs are the Claude jobs:** `claude-review` in `claude-code-review.yml` and `claude` in `claude.yml`. The workflows hold exactly four jobs, and all four fit the agreed names.
  - **No YAML parser:** PyYAML is in `uv.lock` only because other packages need it, and it isn't a declared dependency. The test reads the job level by indentation with the standard library.
  - **What the scanner refuses:** a job's key line with a value other than a comment or anchor, a value left open by `{`, `[` or a quote, a line at column 0 that isn't a key, and a job with `uses:`. A limit that isn't a plain positive whole number, or whose value carries on to a deeper line, counts as no limit. This also refuses some valid YAML, such as a list written over several lines or a quoted number. No workflow here writes one that way, and the error says what to change.
  - **What the scanner doesn't promise:** the first version of this record said any mistake in the scanner fails the test. That was false, and review showed it. It still isn't a parser, and these shapes still fool it: an explicit `? timeout-minutes` line repeating a key, and a tag or anchor alone on a job's first line, which sets the wrong property indent. Neither is written in any workflow here, and neither is worth more scanner code. The alternative is a real YAML parser, which is a dependency decision for the human.
  - **A new job needs a line in the test:** `AGREED_LIMITS` is compared exactly, so a new job or a renamed one fails until someone chooses its limit.
  - **A job that calls a reusable workflow is refused, with or without a limit.** [GitHub's reference](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations) says "you can only use the following keywords in the job containing the call", and `timeout-minutes` isn't among them. There is no such job today. If one is added, the test stops and says a person must decide how to limit it. Whether GitHub rejects the keyword or ignores it wasn't tried.
  - **Not covered:** the limit is on the whole job, so a hang still costs the full 20 minutes and pytest doesn't name the test that hung.
  - **For the human: Done-when 3.** A job past its limit ends `cancelled`, not `failure`, as the Evidence shows. Whether that meets "fails rather than passes" is the human's decision, and the issue's wording is unchanged.
  - **For the human: the `ci.yml:39` comment.** It says the Answer Key guard "shows red". A timed-out `answer-key` would show `cancelled`, going by the `test` job's behaviour. That wasn't tested on `answer-key`, and the comment is unchanged.

## Tests

`tests/test_workflows.py` has 79 tests, up from 29 before review. The full suite had 1184 passing at the time of the round 1 evidence.

- **The real workflows (2):** every job has a limit, and the limits are exactly the agreed ones.
- **The check accepts (25):** limits on every job, at other indent widths, after nested lines and after block text, a quoted key, Windows line endings, and a comment or anchor on a job's key line. Later jobs stay visible past a line separator in a comment, and each job measures its own indent. Values that close on their own line pass, and so do quotes inside plain values. A step's `uses:` isn't mistaken for a reusable workflow. `workflow_files` reads `.yml` and `.yaml` and nothing else.
- **The check rejects (22):** no limit, a limit only in a comment, blank, `timeout-minutes:5`, zero, negative, quoted, an expression, a non-ASCII digit, a no-break space in the key or value, a value carrying on to a deeper line, a limit on a step (three forms), under another key, inside block text, at workflow level, after the `jobs:` block, and a neighbouring job's limit.
- **A workflow it can't read raises (26):** no usable `jobs:` block, or two of them; a job's key line with a value (one line, an open `{`, block text, folded text, an alias); a value left open (`{`, `[`, both quotes, after an anchor, an escaped or doubled quote, on a step, a list item, a comment hiding the `}`, or above `jobs:`); and a line at column 0 that isn't really a key, or sits inside a value.
- **A job that calls a reusable workflow is refused (4):** with no limit, a limit after, a limit before, and a quoted key.

**Block text under a job property hides no limit.** The review asked whether it could. A throwaway check of `|`, `>`, `|-`, `>+`, `|2`, `>1-`, `|1`, `!!str |` and `&x |`, each with the limit at the same indent, deeper, and after some text, agreed with PyYAML in all 27 cases. Text deeper than its key doesn't count, and a line at the key's own indent really is the next key.

**The scanner against a real parser, on generated workflows.** A throwaway script built workflows from awkward line fragments, 400,000 for each of three seeds, and compared the result with PyYAML. It looked for a limit PyYAML doesn't see, or a job the scanner misses. This found the carrying-on bug: 302 such results on the first seed, before that fix, and 40 after it. On all three seeds (40, 30 and 49), every remaining one contained an explicit `? key` line or a tag or anchor alone on a line, the two shapes named in Spec. PyYAML follows YAML 1.1 and stands in for GitHub's own parser, which may differ. For example, PyYAML can't read the U+2028 sample at all, while the scanner gives `{'a': 5, 'b': None}`. The comparison shows what these fragments reach, not that nothing else can fool the scanner.

**Shown live, once, by accident: a job going past its limit.** The plan was to rest this line on the docs, and the issue's wording says it wasn't shown live. That part is now out of date: this PR's own CI hit the limit. Nobody made it happen.

[Run 41886962662](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/actions/runs/41886962662), attempt 1, on commit `fab3624`:

- `test` started at 18:25:13Z and ended at 18:45:31Z, 20m18s later, with conclusion `cancelled`. `answer-key` passed in 6s.
- GitHub's annotation on the job, at level `failure`: "The job has exceeded the maximum execution time of 20m0s". This is what shows it was the limit and not a person cancelling.
- The job was in `Install ffmpeg` from 18:25:23Z to 18:45:27Z, before any test ran, and the later steps were skipped. The log kept printing new package lines until the cancel, reaching download 58 of 89 new packages, out of 69.3 MB. The same step took 17s on the commit before and 16s on the rerun.
- **The cause isn't known.** The log shows a very slow download rather than a silent one, and nothing in it says why. The change in this PR doesn't touch that step, and the rerun on the same commit passed.

**"Fails rather than passes": what each tool reported.** GitHub's conclusion is `cancelled`, not `failure`, so the line isn't met word for word. The job didn't pass, and the run wasn't marked a success.

| Where | What it reported on the cancelled job |
|---|---|
| GitHub's API, job and run conclusion | `cancelled` |
| The job's annotation | level `failure`, as quoted above |
| `gh pr checks 79 --watch` | listed `test	fail	20m18s`, and **exited 0** |
| `gh run watch --exit-status` | exited 1 |
| `gh run view --log-failed` | printed nothing |

**Not measured:** the exit code of plain `gh pr checks 79` on the cancelled job. The rerun started before anyone asked for it, and that command reports the latest attempt: it exits 8 while pending and 0 once passed. The `--watch` exit of 0 means a script that trusts it wouldn't notice this job, though why it exits 0 hasn't been looked into.

GitHub's [workflow syntax docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) agree with the conclusion: `timeout-minutes` is "the maximum number of minutes to let a job run before GitHub automatically cancels it", with a default of 360. One run shows what happened that once, on one job at the 20-minute limit. The 5 and 30 minute limits haven't been reached.

**The rerun.** `gh run rerun 41886962662 --failed`, once. Attempt 2 passed, with `test` taking 1m37s from 18:46:21Z. `ci.yml` and the limit are unchanged.
