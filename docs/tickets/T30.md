# T30: /preflight checks the environment before work starts

[#82](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/issues/82) · PR [#83](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/pull/83) · waiting for human review

A `/preflight` skill that finds setup problems before work starts, using real read-only calls. It reports and never repairs, and something it can't confirm is never a pass.

## Spec

Sessions have lost time to setup problems that only showed up partway through the work: a remote on the wrong host, a plugin enabled but not loaded, and a CI check that passed falsely because it asked the wrong host. It makes no model calls, so it has no Film Budget cost, and it doesn't change the Slack app, the agents or their prompts.

- **Done when:**
  - `/preflight` prints PASS, FAIL or UNKNOWN for each check, with its evidence and the exact fix. It covers the remote, GitHub access, the git hook, the Claude hooks, the toolchain, the skill files and the session tools.
  - The script exits 0 only when every check that ran passed, and non-zero on any FAIL or UNKNOWN.
  - A GitLab `origin` is a FAIL even when `gh` reports success, and a test pins this.
  - GitHub access is a FAIL if `gh repo view` returns a different repo from `origin`.
  - The Claude hooks check sends `block_forbidden.py` a forbidden command and a harmless one, and executes neither. It fails if the forbidden one is allowed or the harmless one is blocked.
  - `/preflight --ci` adds the check runs for `HEAD`: no runs or pending runs are UNKNOWN, a failed run is a FAIL. Without `--ci`, the check is left out and the report says so.
  - Every external call has a timeout, and a timeout is UNKNOWN. A test pins this.
  - It changes no files, settings or credentials, and doesn't read `.env` files.
  - The script uses only the standard library and runs on Python 3.9, tested the same way as the hooks. `ci.yml` runs the new tests in its Python 3.9 step.
  - Each check has tests for both sides: bad input fails and good input passes.
- **Decisions:**
  - Where it lives: this repo first, so it goes through the ticket loop. It could move to user-level skills later, once the repo-specific checks are configurable.
  - Repair: none. It prints the fix and the human or session applies it.
  - When it runs: by hand, not from a `SessionStart` hook, because network calls would slow every session.
  - CI: only with `--ci`, because a new local commit has no runs yet and would otherwise be UNKNOWN on most runs.
  - Session tools: Claude checks its own tool list, because a script can see that a plugin is enabled but not that it's loaded.
  - Reading `ci.yml`: an exact match on the `python-version` line, because the system Python has no PyYAML and T29 found a hand-written scanner unreliable. Anything but one match is UNKNOWN, and a test compares the match with PyYAML's reading of the file.
  - Glossary: "preflight" is a tooling word, so it stays out of `CONTEXT.md`.

## Plan

Tests first, in three groups, each red before its code: the remote, GitHub access and timeouts; then the git hook, Claude hooks, toolchain and skill files; then `--ci`, the exit codes, changing nothing, and the checks against drift. Files: `.claude/skills/preflight/preflight.py` and `SKILL.md`, `tests/test_preflight.py`, the Python 3.9 step in `ci.yml`, the `py39` lint entry in `pyproject.toml`, and a Layout line in `CLAUDE.md`. No effect on cost or prompts.

Changed during Build:

- `uv lock --check` exits 1 for a stale lock and also when it can't resolve offline, so the toolchain check reads the message: a stale lock is FAIL, and anything else it can't confirm is UNKNOWN.
- A timeout also handles `PermissionError` from `os.killpg`, which macOS can raise for a process group that's ending.

Changed during Review, beyond the plan:

- The hook check runs the wired command from `settings.json` through `/bin/sh`, not the script file, because that command is what Claude Code runs. The forbidden command is still only text on its stdin.
- GitHub access reads `GH_REPO` itself, because `gh repo view` ignores it.
- The hook check also reads `disableAllHooks` from `~/.claude/settings.json`, and nothing else from that file. Managed settings aren't read, so a machine-wide policy could still turn hooks off unseen.

## Tests

`tests/test_preflight.py` has 177 tests. Almost all run the script as a subprocess on the machine's `python3` in a throwaway git repo, with fake `gh`, `uv` and `ffmpeg` and a PATH holding only what the test allows. They cover both sides of every check, including a GitLab `origin` with `gh` reporting success, lookalike hosts, a token in a remote, hooks that allow everything or crash, `test` skipped on CI, and a hung child holding the pipe.

Three more guard against drift: the script's reading of `ci.yml` must equal PyYAML's, CI's 3.9 step must name the test file, and the script must parse as Python 3.9 and import only the standard library.

## Close the loop

- **Glossary:** no new terms. "Preflight" is a tooling word and stays out of `CONTEXT.md`.
- **ADR:** none. This is one optional skill, easy to change or remove.
- **Lesson:** Test a checker on what it claims to catch, using the real tool. Every fake passed while `gh repo view` ignored the `GH_REPO` that `gh pr` obeys, and calling the hook's file proved nothing about the wired command Claude Code really runs. A checker's false pass is worse than having no checker, so ask of each PASS what it actually observed.
