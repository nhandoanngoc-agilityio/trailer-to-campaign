# T26: Deploy the Slack app from a release

[#73](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/issues/73) · PR [#74](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/pull/74) · merged

`deploy/t2c-service` runs the Slack front door from a tagged release under `launchd`, so it stays up without a terminal. A stopped service ends a Run waiting for Approval in an error, as Ctrl-C does.

## Spec

- **Done when:**
  - `deploy/t2c-service install <tag>` puts that tag's code in `~/.t2c/releases/<tag>`, installs its dependencies from `uv.lock`, and starts the service. A tag that doesn't exist, or no secrets file, refuses with nothing changed.
  - Installing another tag switches to it, so going back is the same command.
  - `deploy/t2c-service secrets` writes `~/.t2c/env` with mode 600 from the current shell. No secret is printed, or written to the plist or the logs.
  - The service refuses to start if the secrets file is readable by others, or a setting is missing, naming the setting and never its value.
  - `deploy/t2c-service add-film <slug>` copies one Film into the service's home, and refuses a slug that is a path.
  - Stopping the service sends SIGTERM, which ends a Run waiting for Approval in an error, as Ctrl-C does, and never in an Approval.
  - `status`, `logs` and `uninstall` work, and `docs/deploy.md` says how to install, upgrade, go back, and what the limits are.
  - Live: the service runs from a tag, survives a stop and start, and a Run in the test channel completes inside the Film Budget.
- **Decisions:**
  - **"Deploy" means `launchd` on one Mac:** the human chose this on 2026-11-04. No hosted service, no new dependency, and footage stays on this machine.
  - **The service gets its own home, `~/.t2c`:** a throwaway `launchd` job on this Mac got `ls: films: Operation not permitted`, because macOS protects `~/Documents`. Full Disk Access would have fixed it by granting far more than this needs.
  - **So the service keeps its own copy of a Film:** the cost is that a changed Spoiler List needs `add-film` again, or posts are checked against the old list. `status` and `install` warn when a copy differs, but a Marketer in Slack sees nothing. The human may prefer otherwise, since this is a guardrail's data.
  - **Stopping waits for a Run:** the app stops listening, ends a waiting Run in an error, then waits for one mid-stage, up to `launchd`'s 15 minutes. `install` waits too, and if the service won't stop, changes nothing.
  - **A moved tag is refused:** a release is what its tag was. Re-extracting over a running release would be worse than asking for a new tag.
  - **`uninstall` removes the secrets:** they can be written again, and shouldn't outlive the service.
  - **Secrets in a file, not the plist:** `launchctl print` and anything reading the plist can't see them. `launchd` doesn't load `~/.zshrc`, so the service needs a file of its own.
  - **A release is the tag's files, via `git archive`:** no checkout, so nothing there can drift from the tag.

## Evidence

**The rehearsal, under real `launchd`, on 2026-11-04,** with a local tag and dummy secrets, all removed afterwards:
- `install` extracted the tag and installed its dependencies into `~/.t2c/releases/`.
- `launchd` started it, and the release's Python reached Slack, which answered `invalid_auth` to the dummy token. So the service home, the dependencies, `PATH` and the log file all work under `launchd`, and `~/Documents` isn't needed.
- `launchd` retried on its schedule: `state = spawn scheduled`, `last exit code = 1`.
- `~/.t2c` is `drwx------` and `env` is `-rw-------`. The plist holds no dummy value.
- `uninstall` removed the service and the plist.

**A second rehearsal, after `/code-review`'s fixes:**
- Installing over itself stopped and restarted cleanly, with `state = running` and a new pid, so `bootout` followed by `bootstrap` didn't hit a race here. That service wasn't draining a Run, which only the live check can show.
- The stale-Film warning fired on a real copy and cleared after `add-film`.
- A dummy value marked `SECRET` appears 0 times in the whole 56-line log, which holds 2 `invalid_auth` lines, and in no process's arguments.
