# T27: The Bash guardrail reads nested commands

[#70](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/issues/70) · PR [#81](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/pull/81) · draft

A forbidden command nested in other shell syntax now exits 2: inside `$(...)` or backticks, behind a shell keyword, in `eval`, or under a clustered `-c`. A real heredoc body stays text, and normal commands such as `"$py" --version` stay allowed.

## Spec

T24 found these during review and left them out: each passes on `main`'s hook too. The hook is a tripwire for accidents, not a sandbox, so this ticket closes the forms an agent could plausibly write by accident and says plainly what stays out of reach.

- **Done when:** each of these exits 2 under `/usr/bin/python3` and CI's Python 3.9, or this record says why it stays open:
  - `echo "$(git reset --hard)"`
  - `echo '<<EOF'` followed by a line holding the command
  - `if true; then git reset --hard; fi`, and the keywords `then`, `do`, `else`, `elif`, `{`, `!`
  - `eval 'git reset --hard'`
  - `bash -lc 'git reset --hard'`
  - `${x:-git} reset --hard`, `$x reset --hard`, `git ${x:-reset} --hard`
- **And:** real commands from recent sessions replay with no new false blocks. A real heredoc body stays text.
- **Decisions:**
  - **Expansions (the human's call):** an expansion as the program or as `git`'s subcommand is refused only when the visible arguments already look forbidden. `$x reset --hard` is read as `git reset --hard` would be. `git $x --hard` is read as `reset`, `push` and `add` would be, leaving out what's ordinary under other subcommands: `--all`, `--branches` and clusters such as `-Sfoo` or `-uf`. When two words are unknown, as in `"$py" "$script" --all` or `$x $y --force`, the second is likely a file, so only `--hard` still looks forbidden, and `$x $y --hard` is refused while `$x $y --force`, `$x $y origin main` and `$x $y .env` pass. `"$py" --version` passes. A `$x checkout main` doesn't change the branch later commands are judged on, because `$x` may not be git.
  - **An accepted false block, for the human to see:** `git $x origin main` stays refused, as it's pinned on purpose, so `for c in fetch pull; do git "$c" origin main; done` is refused too, though it only fetches and pulls.
  - **On a `main` checkout, an expansion reads as `git` would:** `$x commit -m hi` is refused, and so are `"$docker" push img`, `"$tool" merge a` and `"$x" push`, because those words on `main` are what `git` refuses. Off `main` they all pass. This is a false block we accept.
  - **A path with a literal last part is that program:** `"$root/scripts/sync.sh" push origin main` passes, `"$root/bin/bash" -lc '...'` and `"$HOME/bin/rm" build -rf` are judged as `bash` and `rm`, and `"$root/.venv/bin/pip" install foo` raises the dependency question. A path inside an expansion doesn't count: `$(echo /usr/bin/git) reset --hard` is still an unknown program.
  - **An expansion also reads as a wrapper:** `$SUDO git reset --hard` is judged on what follows it. This goes a step past the issue's examples, at no cost to any replayed command.
  - **rm through an expansion only by rm's own options:** the options before the first positional must all be made of `rm`'s letters. `$x -rf build` and `$x -r -f build` are refused, and `"$py" -m pytest -rf`, `"$FFMPEG" -y -i a.mp4 -r 30 -f mp4 b.mp4` and `"$CC" -O2 -fPIC -rdynamic a.c` pass. `"$GREP" -r -f patterns .` and `"$pytest" -rf` are still refused, false blocks we accept.
  - **`git`'s long value-taking options:** `--git-dir`, `--work-tree`, `--namespace`, `--config-env` and `--super-prefix` now skip their value, so `git --git-dir .git reset --hard` blocks and `git --git-dir "$dir" log -f` passes. A value named like a judged subcommand still reads as the subcommand, so `git --git-dir reset --hard` blocks as it did on `main`, even though `git` itself would reject it.
  - **Wrappers this project really uses:** `caffeinate`, `timeout`, `gtimeout`, `nice` and `uv run` are unwrapped, along with a number after a wrapper (`timeout 5`, `nice -n 5`, `xargs -n 1`). A wrapper also matches by its absolute path, as in `/usr/bin/env`, but not by a relative one, so `scripts/time rm -rf build` passes. `/opt/tools/time rm -rf build` is refused, a false block we accept.
  - **`eval` is that exact word:** `./eval` and `"$t2c" eval` are other programs. So `$x eval 'git reset --hard'` is out of reach.
  - **Blocks `main` had that are gone on purpose:** keeping `$(...)` in its word means what follows it is read as arguments, so `echo $(date) rm -rf build` and `cat $(date)git push -f` now pass. For those, `main` split the command at `)` and read a command no shell would run. What really follows is still read: `echo $(date); git reset --hard` blocks. But the same change does lose blocks on commands a shell really runs, when the program is a wrapper the hook doesn't know: see "A lost block" under Out of reach. And `main`'s heredoc pattern only knew delimiters that start with a letter or `_`, so `cat <<3` then `git reset --hard` then `3` blocked, though that line is a real body, as the shells confirmed. It now passes as text. So does `bash -c 'cat <<EOF` with a body and `EOF'`, which `main` blocked by breaking the quote apart.
  - **No total deadline across `git` calls (the human's call):** several slow calls adding up past the hook's 10 s timeout still pass. The hook is a tripwire for accidents, not a sandbox, and slowing `git` on purpose isn't an accident. Each call still has its 3 s limit, and a timeout blocks.
  - **Text that isn't JSON still exits 0 (the human's call):** as T24 recorded.
  - **`$(...)` is read, and what can't be followed is refused:** T24's lesson was not to teach a guard a language it only needs to refuse. Here the ticket needs what's inside `$(...)`, so the scanner follows quotes and parentheses to find its end, and refuses the rest. It holds no new grammar beyond that: a `case` inside `$(...)`, whose `)` would look like the end, is refused rather than parsed, and so is a comment there holding a `)` or a quote, which the review showed macOS's `/bin/bash` and `/bin/sh` don't treat as a comment.
  - **Heredocs are read by the scanner, not a pass before it:** that is what makes quotes and comments unable to fake one, and it also means any delimiter works (`<<\EOF`, `<<END-OF-TEXT`, `<<'---'`). The delimiter must now match exactly, as in a shell, so an indented `EOF` closes only `<<-`.
  - **A body isn't always text:** with an unquoted delimiter, a shell runs the body's `$(...)` and backticks, which bash, zsh and sh all confirmed. So those are judged, and everything else in the body stays text. The issue didn't name this, but it's the same gap as `echo "$(git reset --hard)"`. With a quoted delimiter the whole body stays text.
  - **Too deep now blocks:** past the nesting limit the hook used to return "no violation". With `$(...)` and `eval` this limit became easy to reach, so it now blocks, and the limit went from 3 to 5.
- **A lost block, out of reach:** `arch $(echo -arm64) git reset --hard`, `lockf $(mktemp) rm -rf build`, `script -q $(mktemp) git reset --hard` and `parallel -j$(nproc) rm -rf {} ::: a b` exit 2 on `main` and 0 here, and the review found a shell really runs them. So do `ssh $(host) git reset --hard` and `docker exec $(docker ps -q) rm -rf /x`, which are likelier to be written, though neither runs on the local checkout. `main` caught them only by accident, splitting at the `)`. A guard reading text can't tell them from `echo $(date) rm -rf build`, because which programs run their arguments isn't in the text, so the hook isn't changed. A test whose name says it's a known gap pins this.
- **Out of reach, on purpose.** These still exit 0, on `main` too:
  - **`(( # )) ; git reset --hard`:** the hook reads `#` as a comment to the end of the line.
  - **An expansion that hides the forbidden part:** `git reset "$mode"`, `git $(echo reset --hard)`, `$x`, `$x --hard`, `eval "$x"`, `bash -c "$x"`, `${x:-git reset --hard}`, `git ${x:-reset --hard}`.
  - **An expansion and the branch:** on `main`, `git ${x:-commit} -m hi`. On a feature branch, `${x:-git} checkout main && git commit -m hi`.
  - **`$SHELL -c 'git reset --hard'`:** reading `$x -c` as a shell would parse `"$py" -c`'s code as shell.
  - **A shell fed some other way:** `bash <<'EOF'` with the command in its body, `echo 'git reset --hard' | bash`, `source reset.sh`.
  - **Programs that run a command later or for you:** `trap '...' EXIT`, `find . -exec git reset --hard \;`, `function f { git reset --hard; }; f`, `$x eval '...'`, `builtin eval '...'`.
  - **Wrappers not read:** `sudo -u me git reset --hard`, whose option value reads as the program, `noglob`, `coproc`, and `echo | xargs -I {} git reset --hard`.
  - **No dependency question through an expansion:** `"$py" -m pip install foo`, `"$pip" install foo`, `"$uv" add foo`.
  - **Options the hook doesn't follow:** `bash -c - 'git reset --hard'`, `bash -eoc pipefail '...'`, `bash -oc pipefail '...'`, `env -u X git reset --hard`, `exec -a x git reset --hard`, `timeout -s KILL 5 git reset --hard`, `uv run --with foo git reset --hard`. The first five ran under bash, sh and zsh with `echo` in their place. The last two are by reading.
  - **A redirect first, or a suffix:** `0</dev/null git reset --hard`, and `git reset --hard$x`, ran under all three. `1<<3 git reset --hard` ran under bash and sh.
  - **A heredoc that closes differently in a shell:** `cat <<EOF`, then `EO\`, `F`, `git reset --hard`, `EOF`, where a backslash-newline joins the delimiter, ran under all three. Under bash and sh, `echo $(cat <<EOF`, `body)`, `git reset --hard`, `EOF`, `)` also runs, because `)` ends the substitution inside what the hook reads as a body. It can't be refused without blocking every `gh pr --body "$(cat <<'EOF'...` that holds a `)`.
  - **zsh only:** `repeat 1 git reset --hard`, `=git reset --hard`, and two `case` forms inside `$(...)`, as the review measured.
  - **Text only, not run:** on `main`, `git $x origin HEAD`, and `git $x evals/expected/a`.
- **Refused though harmless, on purpose.** These exit 2, because the hook can't follow them:
  - `echo $[1<<2]`, `a[1<<2]=3` or `let x=1<<2` with more lines after it. In the first two a `<<` while a `[` is open can't be told from the heredoc in `cat a[1<<'EOF'`, so it's read as a shift and refused if another line follows, and `cat a[1<<'EOF'` with its body is refused the same way. An unquoted `[` that never closes affects any later heredoc in the command too: `ls a[1; cat <<'EOF'`. In the third, `<<` reads as a heredoc that never closes, which is how a shell reads it.
  - `cat <<EOF` with a newline or a body and no closing line. `cat <<EOF` alone exits 0.
  - `echo "$(cat <<EOF` closed by `EOF)"` with no later line holding `EOF`, which bash accepts and zsh rejects. That double-quoted form blocked on `main` too. `x=$(cat <<EOF`, `hi`, `EOF)` and `echo $(cat <<EOF`, `hi`, `EOF)` are refused the same way, though they passed on `main`. With a later `EOF` line the hook reads a body up to it and passes: see the out-of-reach form above, and Evidence.
  - `echo "$(case x in a) echo hi;; esac)"`, and `echo "$(echo time case)"`, whose `time` reads as the keyword.
  - `echo "$(echo `date`)"`, unquoted backticks inside `$(...)`, as they already were outside it.
  - A comment inside `$(...)` holding a `)` or a quote, such as `it's`.
  - A `<<` inside a `((` or `x=(` whose line ends before the `)`: `((a<<2` then `))`. A `((` can span lines: `((1 +`, then `2<<3))` is read as a shift and passes, and the `<<` only has to sit on the line that closes it. Otherwise it might be `((a); cat <<'EOF'`, two subshells and a real heredoc.
  - A `${...}` holding more than plain text inside `$(...)`: `echo "$(echo ${arr[$i]})"`, `echo "$(echo ${x//\//-})"`, `echo "$(echo ${x:-"a"})"`, `echo "$(echo ${x:-$(date)})"`. These passed on `main`, because it never read inside `"$(...)"`. The first two are plausible, but a nested command is read by the same scanner as the top level, where `main` refuses them too. So letting them through would loosen a block `main` had, and they're left for the human. The same goes for an escape in a `$'...'` inside `$(...)`, as in `x="$(IFS=$'\n'; echo "$y")"` and `echo "$(printf $'a\nb')"` with a backslash and an `n`, and for `echo "$(echo do case)"`, whose `do` reads as the keyword. All of them passed on `main`, and tests pin the last three as refused.
- **Slow input, not fixed:** past the hook's 10 s timeout, a run may pass. The review measured two crafted or absurdly repeated inputs. At `5aae339`, 2,000 repeats of `$x commit` took 19.3 s, because each expansion's copy of the state discards its caches, and `"$a " * 7000 + "eval 'git reset --hard'"` took 12.1 s, because the expansion loop is quadratic. At `8970b91`, the same inputs took 8.9 s and 0.4 s.
