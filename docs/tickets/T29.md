# T29: Every CI job has a time limit

[#78](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/issues/78) · PR [#79](https://github.com/nhandoanngoc-agilityio/trailer-to-campaign/pull/79) · draft PR, in review

Every job in every workflow now sets `timeout-minutes`, and a test fails if one doesn't, so a hung test costs at most 20 minutes of CI rather than GitHub's default of 6 hours.

## Spec

Found in the review of PR #76: no workflow set a limit, and pytest has no timeout of its own.

- **Done when:**
  - Every job in every file under `.github/workflows/` sets `timeout-minutes`: 20 for `test`, 5 for `answer-key`, and 30 for the Claude jobs.
  - A test fails if a job in any workflow has no `timeout-minutes`, and it adds no dependency.
  - A job that goes past its limit fails rather than passes. This rests on GitHub's documented behaviour; the record says it wasn't shown live.
- **Decisions:**
  - **The numbers:** the human approved 20, 5 and 30. The slowest of the last 31 PR runs of CI took 235 seconds, so 20 minutes leaves about five times that.
  - **Which jobs are the Claude jobs:** `claude-review` in `claude-code-review.yml` and `claude` in `claude.yml`. The workflows hold exactly four jobs, and all four fit the agreed names.
  - **No YAML parser:** PyYAML is in `uv.lock` only because other packages need it, and it isn't a declared dependency. The test reads the job level by indentation with the standard library.
  - **What the scanner does when unsure:** anything it doesn't recognise counts as no limit or raises, so a mistake in the scanner fails the test rather than passing it. It also rejects some valid YAML, such as a job written on one line or a quoted number. No workflow here writes one that way.
  - **A new job needs a line in the test:** `AGREED_LIMITS` is compared exactly, so a new job or a renamed one fails until someone chooses its limit.
  - **Not covered:** the limit is on the whole job, so a hang still costs the full 20 minutes and pytest doesn't name the test that hung. A job that calls a reusable workflow may not be able to set `timeout-minutes`: the part of GitHub's docs we read for such jobs doesn't list it, though it doesn't claim to be a complete list. There is no such job today. If one is added, this test will flag it and that needs checking then.

## Tests

`tests/test_workflows.py` has 29 tests. The suite had 1134 passing at the time of the evidence below.

- **The real workflows (2):** every job has a limit, and the limits are exactly the agreed ones.
- **The check accepts (3):** a limit on every job, a comment after the value, a limit after nested lines, another indent width, and a top-level key after `jobs:` not read as a job.
- **The check rejects (19):** no limit, a limit only in a comment (whole-line, after another key, or as the value), a blank value, `timeout-minutes:5`, zero, negative, quoted, an expression, a limit on a step (three forms), under another key, inside block text, at workflow level, after the `jobs:` block, a neighbouring job's limit, and a job written on one line.
- **A workflow it can't read raises (5):** no `jobs:`, `jobs:` only in a comment, an empty block, `jobs:` on one line, and a job that isn't a key.

**The scanner against a real parser.** A throwaway script, not committed, read the same files with PyYAML from the virtualenv. The two agreed on all three:

```

```

**No dependency added:** `git diff --stat origin/main -- pyproject.toml uv.lock` prints nothing.

**Not shown live: a job actually going past its limit.** That line of the Done-when rests on [GitHub's workflow syntax docs](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), which call `timeout-minutes` "the maximum number of minutes to let a job run before GitHub automatically cancels it", with a default of 360. So the documented outcome is a cancelled job: it doesn't pass, but the docs say "cancels" where the Done-when says "fails", and we haven't seen how such a run is shown. We didn't make CI hang to find out. The tests prove that the limits are set, not what GitHub does at one.
